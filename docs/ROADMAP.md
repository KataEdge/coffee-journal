# 複数ユーザー対応 機能追加ロードマップ

> 他のセッション/エージェントが参照できるよう、機能追加の優先順位と依存関係をまとめたドキュメント。
> 各フェーズに着手する際は、このドキュメントを起点に詳細な実装プランを別途作成すること。

## Context

現在のCoffeeJournalは実質シングルユーザーのアプリになっている。`Domain/Repositories/AuthRepositoryProtocol.swift` は定義済みだが実装がなく、`App/CoffeeJournalApp.swift` はログイン画面を経由せず直接 `MainTabView` に入り、`CreateNoteViewModel` は投稿のたびにランダムな `UUID` を `userId` として払い出している（＝ユーザーという概念が永続化されていない）。

「利用者が複数人に増えた際に欲しくなる機能」として15個の機能案が出ているが、そのうち半数以上（他ユーザーいいね・フレンド・ランキング・コミュニケーションの場・ログイン時アバター等）は「実在する別々のユーザー」が存在することが前提になっている。したがって認証基盤を最優先の土台とし、その上に依存関係の浅いものから積み上げる順で優先順位をつけた。

決定事項：
- 評価の10段階化は、既存の5つの `TasteParameter`（酸味/甘み/苦味/コク/香り）を全て1〜10に変更する（総合評価スターは新設しない）。
- 「カフェ好き同士のコミュニケーションの場」はタイムライン/フィード型（他ユーザーの投稿が流れてくる形式）を目指す。

## フェーズ構成と優先順位

### Phase 0（最優先・ブロッカー解消）: 認証基盤
- アカウント作成・ログイン機能（Supabase Authを用いた `SupabaseAuthRepository` の実装、ログイン/サインアップ画面、セッション管理）
- ログイン時のアバター作成（`UserProfile.avatarUrl` を設定するオンボーディングフロー）

**理由**: 他ユーザーいいね・フレンド・ランキング・ステータスアップ・タイムライン等、要望の過半数がこれに依存する。`AuthRepositoryProtocol` は既にI/Fがあるため、実装は「協約に沿ってSupabase実装を書く」作業になる。`Domain/Entities/UserProfile.swift` と `profiles` テーブル（RLSは `auth.uid()` 前提で既に設計済み — `supabase-schema` スキル参照）もそのまま使える。

### Phase 1: 低コストな穴埋め・独立機能
- 投稿の編集・削除機能のUI配線（`CoffeeRepositoryProtocol.update`/`delete` は実装済み、`TastingNoteDetailView` に編集導線、一覧にスワイプ削除等を追加するのみ）
- コーヒー評価を5→10段階に変更（`TasteParameter.swift` の5軸を1-10に、`CreateNoteView` の入力UIと `TasteRadarChart` の表示スケールを追随）
- ハンドドリップ／エスプレッソ以外のタグを追加（`CreateNoteViewModel.availableBrewMethods` へ追加するだけ）
- テーマカラー変更機能（`Color.amberAccent` 依存箇所を置き換え、`AppStorage` でユーザー設定を永続化）

**理由**: いずれも既存の実装/協約を流用でき、認証実装と並行または直後に着手可能。特に評価スケール変更はデータ件数が少ない今のうちに済ませておく方が後々のマイグレーションコストが低い。

### Phase 2: メディア投稿強化
- 画像・動画投稿（AWS S3）— `Domain/Repositories/StorageRepositoryProtocol.swift` の実装、`aws-s3-upload` スキルの presigned URL フローに沿って実装

**理由**: I/Fとキー命名規則（`tasting-notes/{user_id}/{UUID}.jpg`）は既にPhase 0の認証（実ユーザーID）を前提に設計済み。UGCの質が上がり、後続のいいね／ランキング／タイムラインの訴求力が上がる。

### Phase 3: ソーシャルコア（反応機能）
- 他ユーザーによるいいね機能（`likes` テーブル新設、投稿×ユーザーの一意制約、RLSで自分以外の投稿にも書き込み可）
- お気に入り機能（`favorites` テーブル、いいねとほぼ同じ設計で実装効率が高い）
- いいねが多い珈琲店のランキング表示（いいね数の集計クエリ、カフェ単位で集約）

**理由**: 認証がないと「誰が」いいねしたか区別できない。いいねの仕組みができればお気に入りは同型のテーブルで低コストに追加でき、ランキングはその集計として自然に続く。

### Phase 4: つながり・継続利用施策
- フレンド機能（フレンド申請／承認テーブル、フレンド一覧）
- 記録したカフェの数に応じたステータスアップ（ユーザーごとの投稿数集計とレベル/バッジ表示）

**理由**: 認証・いいねの基盤の上でユーザー同士のつながりと継続利用インセンティブを強化するフェーズ。ステータス集計はユーザーIDが安定していないと意味を持たない。

### Phase 5: タイムライン型コミュニティ
- カフェ好き同士が交流できる場（他ユーザーの投稿が流れるフィード＋投稿への社会的コメント機能。既存の「コメント」欄は投稿者本人の私的メモなので、これとは別に新しいコメントモデルを設計する）

**理由**: フィードUIと社会的コメントは、認証・いいね・フレンドが揃って初めて価値が出る大型機能。依存の多さから中盤〜終盤に配置。

### Phase 6: データ活用・コンテンツ拡充
- レコメンド機能（いいね・お気に入り・フレンド等の蓄積データを踏まえたカフェ/コーヒーのレコメンド）
- コーヒーに関する記事・コラムの表示・作成機能（他の要望と依存関係が薄いCMS的機能）

**理由**: レコメンドは十分な行動データが溜まってから精度が出る。記事・コラムはコアのソーシャルループと独立しており、リソースが空いた時に着手すれば良い。

## 進め方（各フェーズ共通）
- 各機能は `feature/...` トピックブランチで着手し、`swift test` を通してから `main` へPR（`github-flow` スキル参照）。
- 新規機能は `Domain`（Entity/Repository protocol）→`Data`（DTO/Supabase実装）→`Presentation`（ViewModel/View）の順で実装し、`swiftui-feature-scaffold` スキルの雛形に従う。
- 新テーブル追加時は `supabase-schema` スキルのRLS設計指針に従う。
- 画像/動画アップロードは `aws-s3-upload` スキルの手順を厳守。
- シークレット（Supabase/AWSキー等）は `secret-management` スキルとGitleaksチェックに従う。

## 検証方法
- 各フェーズ完了時に `swift test` を実行し既存テストが通ることを確認。
- 新規リポジトリ実装には対応するMockとXCTestを追加（`testing-harness` スキル参照）。
- UIを伴う機能（編集/削除導線、テーマ切替、フィード等）はシミュレータで実際に操作し、golden pathとエッジケース（未ログイン状態、他人の投稿への操作制限など）を目視確認。
- 認証やRLSに関わる変更は、Supabase側でポリシーが意図通りか（自分の投稿だけ編集/削除できるか等）を実データで確認。
